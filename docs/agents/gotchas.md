# API & Type Gotchas
> Detail reference moved out of AGENTS.md. Read before changing the WebSocket/REST clients, MCP argument handling, automation/script/scene/dashboard handlers, call_service/Smart Wait, registries, statistics or trace code. Helper and Config Entry gotchas live in `helpers-gotchas.md`. Convention: an entry is a terse rule plus a one-line reason, not a narrative; the "how we found it" story belongs in commit/PR history. Add an entry only for a non-obvious trap likely to recur.

## Gotchas

- **Pagination**: `PaginationMetadata.NextCursor` is `*string` - requires nil check and dereferencing
- **WS send order = ID order**: ID allocation, pending registration and `conn.Write` happen under one send semaphore (`sendSem`; HA rejects a non-increasing id with `id_reuse`). Never write with the caller's ctx (coder/websocket closes the whole conn when a write ctx expires) - writes use the session ctx + `WriteTimeout`. `Connect(ctx)` bounds only dial/auth; lifetime ends at `Close()`. Pre-send failures are `notSentError` (retryable); post-send connection loss is retried only for read-only types (`isReplaySafeWSCommand`, `ws_replay.go`, deny-by-default: every `*/list` plus an explicit set) - a write fails with `errOutcomeUnknown` and is never re-sent, because it may already have been applied; a new read command must be added to that set to get retries. `auth_invalid` (`errAuthFailed`) stops the reconnect loop and is stored in `WSClient.authErr` (set under `mu` before `reconnecting` goes false, cleared by `installSession`), so `WaitForConnection` returns it at once instead of polling to its 10s limit. The pool evicts only `!IsUsable()` clients (not connected **and** not reconnecting).
- **`CachedClient` invalidation on new mutating methods**: any new write/service method added to `cached_client.go` must `defer c.InvalidateRegistryCaches()` (unconditional - a failed write has an unknown outcome); a plain delegation serves stale registry data for the TTL. Services/config caches clear only on reconnect, via `withReconnectInvalidation` in `factory.go` - set `WSClientConfig.OnReconnect` before `Connect`, never `WSClient.SetOnReconnect` on a live client (unsynchronized write, races the reconnect loop).
- **Person attributes**: `device_trackers` is `[]any` requiring type assertion, not `[]string`
- **HA silently strips label ids missing from the label registry**: `config/{area,entity,device}_registry/{create,update}` subtract unknown ids from `data["labels"]` and return success, so a bad id is an invisible no-op (issue #242). `labelWriteGuardError()` (`internal/handlers/labels_validation.go`) rejects caller-supplied labels pre-write; it returns a `labelGuardResult{Refusal, Warning}`, not a bare `*mcp.ToolsCallResult` - `Warning` is non-empty when the registry couldn't be (re-)verified and the write proceeded unchecked, and callers must `appendResultWarning` it onto their success result rather than reporting bare success (a silent degrade would recreate the exact invisible-no-op bug #242 fixed). Before refusing, the guard retries once against a freshly-invalidated registry via an optional `interface{ InvalidateLabelRegistryCache() }` type assertion (`CachedClient.InvalidateLabelRegistryCache`, exported for this purpose) - the label registry shares `HA_CACHE_AREA_REG_TTL_MIN` (there is no dedicated label TTL), so a label created moments ago in the HA UI would otherwise be refused as "unknown" for up to that TTL. **`labels` must be parsed with `parseLabelsArg`, never `getStringSlice`/`toStringArray`**: a bare string or an array containing a non-string element must be refused outright, not silently reduced to a zero-length-but-non-nil `[]string` - that zero-length slice bypasses the guard's own `len(supplied)==0` exemption, and on update `ws_client_impl.go` sends `params["labels"]` for any non-nil `config.Labels` (even empty), so a malformed input previously wiped every existing label instead of being rejected. Integration tests must mint real labels via `s.CreateTestLabel()` instead of inventing strings.
- **`buildDeviceIDsInArea`**: must return errors from `GetDeviceRegistry`, not swallow them - a swallowed fetch failure silently narrows `query_entities`'s `area_id` filter instead of failing the query.
- **Client interface method additions**: touches 12 files - `client.go`, `ws_client_impl.go` (if WS-backed) + `rest_client.go`, `hybrid_client.go`'s `WSOperations`/`RESTOperations` + delegation, `cached_client.go` delegation, and 6 test mock files.
- **`wsClientImpl` implements `WSOperations`, not the full `Client` interface**: REST-only ops (`GetScene`, `GetServices`, `RenderTemplate`, `GetConfig`, automation/script/scene create/update/delete) live only on `HybridClient`'s `RESTOperations`; automation/script reads and list ops are WS - don't add a method to `WSOperations` unless a real WS command backs it.
- **`ContentBlock` custom `MarshalJSON`** (`internal/mcp/types.go`): don't remove it - it is what keeps emitting the `"text"` key for an empty string despite the struct tag's `omitempty`; the MCP spec requires the key, and omitting it causes `invalid_union` errors in MCP clients.
- **HACS download API field**: `hacs/repository/download` requires `repository` (not `repository_id`)
- **Automation/Scene entity ID derivation**: HA derives entity IDs from alias/name (slugified), not from config ID. Use `generateAutomationID(alias)` to keep them in sync.
- **List operations don't populate Config**: `ListAutomations()`/`ListScenes()`/`ListScripts()` return State/EntityID only - use `Get*()` for full config.
- **Script entities never expose `sequence` as a state attribute**: don't read `script.Attributes["sequence"]` from `ListScripts()` - fetch via `GetScript()` per script instead.
- **`find_references` scanners that fetch config by config must stop on a dead ctx**: they skip per-config fetch errors, so a fetch that failed only because ctx ended would drop that config and read as a complete scan. Return `(hitsSoFar, errScanInterrupted(ctx, source))` when `ctx.Err() != nil` so the source lands in `failed_sources`. The handler also runs the scan under its own `scanTimeout` (25 s), which must stay below the HTTP `httpWriteTimeout` (30 s), or the server closes the connection with an empty reply.
- **The `helper_template` scan costs about two REST requests per template helper**: `GetConfigEntryOptions` runs a full options flow (init + abort) per helper, all under the one shared REST rate limiter (10 req/s default). Concurrent `find_references` calls scanning `helper_template` therefore slow each other down linearly and past ~`scanTimeout` report it in `failed_sources` (correctly, not a bug) - a concurrency test must not fan that source out across many calls.
- **Trace list API requirement**: `trace/list` requires `domain`; the handler schema marks it optional because `resolveTraceListParams` derives it from `entity_id` and errors when neither is given. `wait=true` polls until traces appear (HA records them asynchronously).
- **Trace `item_id` is the `unique_id`, not the `entity_id`**: a wrong key returns an empty list, not an error. `resolveTraceItemID()` resolves this via `GetEntityRegistryEntry` - don't bypass it.
- **The server rejects argument names absent from `InputSchema.Properties`** (`mcp.UnknownArguments` in `handleToolsCall`, mirrored by integration `CallTool`), and then rejects values whose JSON type or `enum` the schema rules out (`mcp.InvalidArguments`, `arg_type_validation.go`; also mirrored by `CallTool`, on the JSON-round-tripped args). It rejects only what no handler could coerce: numeric strings for `integer`/`number`, a number for a `string` and the loose boolean spellings (`yes`/`off`/`0`/`1`) are not rejected (a handler without an `argReader` may still ignore them), `null`/`""`/`[]` count as not supplied (like `isAbsentArg`), and array elements and object contents are not checked - so the handler-level strict parsers (`parseLabelsArg`, `parseStatisticIDsStrict`, `argReader`, ...) stay. A schema enum or type that is narrower than what the handler (or Home Assistant) accepts is now a server-side rejection of a valid call, so widen it with the handler: a case-insensitive value cannot be an enum, and a new HA value must be added to the enum. A property that accepts several JSON shapes (e.g. a string or an array) must omit `Type` and be listed in `untypedByDesign` (`tool_schema_types_test.go`), since `mcp.JSONSchema` has no `oneOf`; `TestToolSchemas_EveryPropertyIsValidatable` fails on any other untyped property. An undeclared arg a handler reads is unreachable for real clients; `TestToolSchemas_DeclareEveryLiteralArgRead` pins it, and a new handler file must be registered in its `auditFileOwners`.
- **Mode/type-specific args go through `rejectInapplicableArgs`** (`arg_applicability.go`). An arg the active mode doesn't read is an error, never a silent drop; `format`/`verbose` are exempt, `nil`/`""`/`[]` count as absent while `0`/`false` are real values.
- **`GetLogbook` takes `[]string`; REST sends `entity=a,b`** (HA parses it with `cv.entity_ids`), nil = all entities. `get_logbook` caps `entity_ids` at 100 (`maxEntityIDsPerCall`), and its pagination cursor hashes the sorted ids.
- **`call_service` merges `target` into `data` in the handler** (`buildServiceData`, target wins as in HA core), so `extractEntityTargets`, the Smart Wait snapshots and the `return_response` path all read one map and the `Client` interface stays unchanged. Both `data` and `target` are type-checked there: a non-object is refused (a silently dropped `data` would run e.g. `homeassistant.turn_off` with an empty target), and `data: null` counts as absent while `target: null` is an error.
- **Services exempt from the Smart Wait poll live in two places in `waiter.go`**: the `servicesWithoutTargetStateChange` table (exact `domain.service` pairs) and a domain rule in `serviceChangesTargetState` (every `script` service except `turn_off`, since script object ids can't be listed). They leave the target's state alone, so polling can only time out into a false warning. `automation.turn_on`/`turn_off`/`toggle` and `script.turn_off` do flip state and are deliberately not exempt.
- **Todo `uid`→`item` API field rename**: user param `uid` maps to `data["item"]` in `todo.update_item`/`remove_item` - never pass `item` directly.
- **Empty array parameter handling**: create rejects empty required arrays; update allows an empty array to clear a field.
- **HA registry-update enum fields accept only `null` or the enum value, never `""`**: `config/{entity,device}_registry/update`'s `disabled_by`/`hidden_by` validate `vol.Any(None, "user")` - an empty string fails coercion ("not a valid value at 'disabled_by'; Got ''") and rejects the whole update (issue #264). The tool arg `"none"` maps to an empty-string sentinel that `ws_client_impl.go`'s `enumUpdateValue` serializes as JSON null (clear); a caller-supplied `""` arg is treated as unset and omitted. Keep the sentinel→null translation in `enumUpdateValue`, not in the handlers.
- **Unmodeled automation/script keys pass through verbatim**: `trigger_variables`, `initial_state`, `max_exceeded`, `trace` and future HA keys live in an unexported `extra` map on `AutomationConfig`/`ScriptConfig` and are re-emitted by `MarshalJSON`; the known-key set is derived from the json tags (`knownConfigKeys`), so never hand-list keys - HA's config write is a full replace, and a key the struct drops is deleted by any update/patch. Both configs decode through a method-less alias type, so a new tagged field needs no decode code.
- **Automation/script key order is semantic, and the write paths must carry it** (issue #311): HA renders `variables` sequentially in dict order, and Go's `encoding/json` sorts map keys, so any map-based round trip silently reorders them. `AutomationConfig`/`ScriptConfig.KeyOrder` (a `jsonorder.Order`) is captured on decode, updated by `jsonpatch.ApplyWithOrder`, and used by their `MarshalJSON`; the caller's own order comes from `mcp.ArgumentOrderFromContext`. Rules: reassign `KeyOrder` after `mapToStruct` (its `UnmarshalJSON` captures the *sorted* order of the marshaled map); a subtree replaced from args takes the caller's order or nil, never HA's old order applied by index; no-op checks compare ordered bytes (`orderedConfigEqual` for patch; `json.Marshal(*config)` before/after in `applyAutomationUpdateOrdered`/`applyScriptUpdateOrdered` for update), so identical content in a different key order now writes (and resets `for:` timers) - that is how a sorted automation gets repaired. A missing or partial order falls back to sorted keys, never worse than before. Dashboards/scenes are not covered (their key order is cosmetic).
- **`manage_automation`/`manage_script` `update` stay merges and name what they carried over**: `keptKeysNote` (`config_kept_keys.go`) appends `(kept from previous config: ...)` for every top-level key outside `automationOwnedKeys`/`scriptOwnedKeys` (the keys `update` has an argument for), because HA's config write is a full replace and a silent carry-over reads as "nothing else existed". `manage_automation`'s `variables` argument replaces the whole block on `update` (`{}` or `null` removes it, omitted keeps it) and is then not "kept"; `manage_script`'s `variables` argument is execute-only and is never config, so a script's `variables` block can only be kept.
- **Writing an id absent from the managed config file silently orphans instead of editing**: `POST /api/config/{script,automation,scene}/config/<id>` appends a new `<id>_2` entry rather than failing when `id` isn't a key in that config file (YAML-defined/`!include`d entries). `update`/`patch` guard with `configWriteGuardError()`/`ConfigFileEntryExists` (scripts/automations) or a `GetScene`-first read (scenes) before writing.
- **A config DELETE sent right after a config POST orphans the entity**: HA schedules its own async reload after `POST /api/config/{automation,script}/config/<id>`, and a DELETE landing inside it (observed up to ~250ms after the POST) returns 200 but leaves a live entity with no config behind (later 400 "Resource not found"). Product `update`/`patch` are safe because they reload synchronously; integration tests that call `UpdateAutomation`/`UpdateScript` directly must reload (`automation.reload` with `id`, `script.reload`) before the cleanup delete. `cleanup.go`'s registry fallback is only a logged safety net, not the fix.
- **`manage_script`/`manage_scene` `update`/`patch` resolve by alias/friendly-name the same way `get` does** (`resolveScriptForWrite`/`resolveSceneForWrite`), gated on a confirmed not-found (not any error) and refusing rather than guessing on an ambiguous match.
- **`manage_scene update` reads via `GetScene` and merges onto the fetched config** (`applySceneConfigUpdates`), not a rebuild from `GetState` - HA's scene config write is a full replace, not a merge, so the old path wiped `entities`/`icon`/`metadata`.
- **REST identifiers are URL-escaped** (`neturl.PathEscape`, aliased to avoid `gocritic importShadow`) - an unescaped id like `../automation/config/1` would let one tool's write path bypass another tool's `ToolFilterEngine` blacklist.
- **`isNotFoundError` keeps a substring fallback even for `APIError`**: HA's config-file `DELETE` returns a **400**, not 404, for YAML-defined/orphan scripts - a strict status-code check would break that fallback.
- **`RESTClient`'s `http.Client` must never leave `Transport` nil** - a nil `Transport` falls back to the shared `http.DefaultTransport`, and `httptest.Server.Close()` unconditionally calls `http.DefaultTransport.CloseIdleConnections()` - not scoped to its own connections. Under `t.Parallel()` REST-client tests (separate `httptest.NewServer` each), one subtest's teardown could silently kill another's still-in-flight connection (flaky `HTTP/1.x transport connection broken`, issue #227). `NewRESTClientWithConfig` clones `http.DefaultTransport` per client for an isolated connection pool.
- **REST retries only idempotent requests**: `isRetryableRESTError` retries GET/HEAD on any transient failure (429, 500/502/503/504, network errors; not client timeouts), other methods only on 429 and dial errors - replaying a config POST/DELETE after a 5xx or timeout could apply it twice. `IsRetryableError` must fall through to message matching for non-timeout `net.Error`s, because every real transport error (`*url.Error`, `*net.OpError`) implements `net.Error`.
- **Retry settings reach clients only through `cmd/ha-mcp/client_config.go`**: always start from `DefaultWSClientConfig()`/`DefaultRESTClientConfig()` (a zero `WSClientConfig` disables auto-reconnect and pings) and give pooled clients the WS config via `WithWSConfig`. The app logger and the cache config travel the same route: the builders take the logger, and `buildCacheConfig` feeds both `newClientPool` and `buildClientOptions` (the default-client path), so a client built elsewhere silently loses logging and caching.
- **`recorder/list_statistic_ids` merges integration-provided metadata with `statistics_meta` rows** - an id can be listed with zero recorded data, and an id whose metadata comes from an integration fallback (not the DB) is still listed after `recorder/clear_statistics`, which only purges DB rows + metadata. Don't assert list-absence after a clear, and don't treat listed-but-dataless ids as a bug (pinned by `TestManageStatisticsLifecycle`'s comments).
- **`manage_statistics:clear`**: use `parseStatisticIDsStrict` (`statistics.go`), not the read path's lenient `parseStatisticIDsLenient` (`entities_consolidated.go`) - the latter silently drops bad elements, which is wrong for an irreversible purge. Also not matched by a `manage_*:delete` filter glob (action name is `clear`, not `delete`) - block `manage_statistics:clear` explicitly if a policy needs it excluded. `clear` also cross-checks requested ids against `recorder/list_statistic_ids` before purging (`resolveKnownStatisticIDs`) so the success message can report which ids the recorder actually had vs. skipped, and supports `dry_run: true` to preview that split without purging - a pre-check fetch failure degrades to the pre-check-less behavior with an appended `WARNING:` line rather than blocking the clear. `parseStatisticIDsStrict` splits ids into `valid` (matches HA's statistic_id shape) and `unrecognized` (doesn't) rather than hard-failing the whole batch on a single shape mismatch - an orphaned statistic can carry an id shape older or buggier than HA's own validator currently allows, and cleaning that up is this tool's purpose; `resolveKnownStatisticIDs` against the recorder's real id list is the actual correctness gate, not the regex. Only when *every* id is unrecognized does the call still error, since nothing would be left to act on. Every element is also bounded by `maxScalarStringLen` - `maxClearStatisticIDs` only bounds element count, not length.

- **`manage_dashboard` has two identifiers, and a config read/write must never default silently**: the collection `dashboard_id` (list/create; update/delete) and the `url_path` (what `lovelace/config[/save]` takes). `get`/`patch`/`save_config`/`find` resolve the target through `resolveDashboardTarget` (`lovelace.go`), which maps `dashboard_id` → `url_path` via `ListDashboards` and refuses non-string, unknown or conflicting values - a bare `args["url_path"].(string)` read turns a wrong type or wrong key into `""`, i.e. the default dashboard, and `patch`/`save_config` would then overwrite it behind a success message. Unknown arg names (e.g. a skill teaching `dashboard_url_path`) are rejected by the server, so embedded skill examples in `internal/handlers/skills/` must use the real parameter names.

## Registry and detail-map patterns

**Entity registry update response**: `UpdateEntityRegistryEntry()` returns the updated `EntityRegistryEntry` (HA wraps response in `entity_entry` key, correctly unwrapped by wsClientImpl); after entity_id rename use `RemoveEntityRegistryEntry()` not `DeleteHelper()`

**Config Entry group cleanup**: Config Entry helpers (groups included) are deleted by `HybridClient.DeleteHelper`, which finds the entity's `config_entry_id` in the entity registry and calls `DeleteConfigEntry`; the bare WS `DeleteHelper` rejects non-WS platforms up front. `RemoveEntityRegistryEntry()` only removes the registry entry and leaves the config entry behind, so it is a last-resort fallback (integration `cleanup.go`), not the default

**Registry tool name resolution**: When adding name-based lookup to registry tools (`manage_*`), use two-phase pattern: `find<Type>ByInput(items, input)` (exact ID → case-insensitive name substring) + `resolve<Type>ID(ctx, client, input)` for update/delete

**Detail map field collisions**: When building detail maps from state attributes, check for field name conflicts with reserved keys (`entity_id`, `state`, `friendly_name`) — rename attribute values to prevent overwriting
